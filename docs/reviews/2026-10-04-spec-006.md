# Review of spec 006's implementation (2026-10-04)

The owner asked, before merging [PR #7](https://github.com/cbgithub7/oneframe-lab/pull/7), whether
the implementation of [spec 006](../../specs/006-foundations/spec.md) does what it is meant to, how
it fits the plan in [the handoff](../handoff.md), and how it fits the project's rules
([AGENTS.md](../../AGENTS.md)).

Six reviewers read the branch's code and ran it:

- four took the requirements in pairs: the root and what is written outside it; formats and
  processes; failures and evidence; cache keys and the quality of the tests;
- one judged 006 against the plan, the [review of 2026-10-02](2026-10-02.md) and spec 003;
- one judged it against the rules and the code's style.

Each finding rated medium or higher then went to a second reviewer told to refute it. One was
refuted; the rest held, each at a lower severity. Nothing rated high survived. The owner accepted
the recommendations below on 2026-10-04, and the fixes landed in the same PR.

## Verdict

**It does what it is meant to.** The seven requirements are in the code, and every acceptance
criterion has tests that fail when the feature breaks. Beyond the tests:

- the engine's and the app's root functions gave the same answer for 20,000 random inputs, mixed
  slashes, drives, shares, `.` and `..`, on three platforms;
- the real app, run on Linux under `strace` with every home and temporary folder in a sandbox, wrote
  its user data, session data, crash dumps, logs, uv's lock and all bytecode under the root;
- the per-process folders repair themselves after a crash, and the cross-process locks hold on both
  systems.

**It fits the plan.** It closes section 8B and the storage problems of section 5 of the earlier
review. Spec 003 finds what it needs in the layout, the locks, the formats, the failure model and
the journals. Neither spec 004 (a long-lived worker) nor first light has to undo any of it.

**It keeps the rules.** The engine still imports nothing heavy, every Python text open says
utf-8, the page still has one door, no test was weakened, no dependency was added, and nothing
outside a node's folder names a model.

## Found, and what was done

**Fixed in the PR:**

1. The footprint test (AC2) inherited CI's `UV_CACHE_DIR`, so it could not catch a dropped uv
   cache setting; it now clears every outer `UV_` variable and checks the root's uv cache.
2. A person's own `HF_HUB_CACHE`, `TRANSFORMERS_CACHE`, `HF_MODULES_CACHE`, `TRITON_CACHE_DIR` and
   the like reached runtime children, where each overrides the cache folders set under the root: a
   run could read weights Download never fetched. They are now removed, and reserved.
3. An engine crash during a run was missing from the run's journal; it is now its last line.
4. Start failures other than a refused root reached the page with no reason, and a page that
   subscribed after the engine failed (uv missing, say) waited forever. Every start failure is now
   an `engine.failed` with a reason, and the page's first request answers with it.
5. A second launch on the same root started a second engine; it now opens nothing.
6. A full journal dropped the very failure it is kept for; how a run ended is now written past
   the cap, within a bound.
7. A node's code hash could miss an edit that kept a file's size and time, and did not follow a
   linked folder; it is now read from the files once per run, following links but not loops.
8. `diagnose` missed a user name percent-encoded in a `file://` URL and WSL's `/mnt/c/Users/...`.
9. Nothing checked that the engine gives the scheduler its runtime keys; a test does now.
10. The docs claimed more than was shown: the handoff said the footprint test proves Electron's
    folders (it never starts Electron); spec 006 said it answers all of section 4; a third changed
    test was unlisted; AGENTS.md lost the note that guarded deletes wait for packaging; nothing said
    when a format goes up. Each is corrected.

Found while checking these in the real app: every start sent two requests to Google for spelling
dictionaries. The spellchecker now has no languages, and the app made none.

**Decided by the owner:** the graphics driver's shader cache (`~/.cache/mesa_shader_cache`,
NVIDIA's and Direct3D's caches) is an accepted exception to the storage rule. The driver owns and
caps it, every program shares it, and the GPU process starts before the app's code can move it.
The NSS certificate database one reviewer saw did not reproduce: the app makes no TLS connection.

**Refuted:** that library caches can be kept under the root only by editing the engine. A runtime
can point one at a folder relative to the job, or a node can set it before importing the library.

**Open, and tracked in [the handoff](../handoff.md):**

- the npm tools leave uv's lock file in the system temporary folder;
- a `memory` failure says `retry` even when this machine can never run the node;
- a step log has no bound while its run lasts;
- disk and lock errors are reported as engine bugs;
- on Windows, a library cache outside the variables `child_env` sets goes to the person's profile;
- a runtime node running in one process is not protected from a remove in another;
- spec 003 lists `stopped` as a failure reason, which 006's model does not allow;
- what spec 004's worker must keep of 006's one-process-per-job assumptions;
- the items of the earlier review's section 4 that 006 did not take on, now listed in the handoff.

## Unverified

The real app on Windows is still to be run; the spec's Verification gives the steps. No GPU was
used, so the shader cache was seen with Mesa's software renderer only.
