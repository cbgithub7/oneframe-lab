# Review of the project as a whole (2026-10-02)

The owner answered spec 003's eight questions and then asked for a second round of review: of
spec 003 again, of its downloader decision, and of the project as a whole. The project was judged
against its end goal, professional development and maintainability, clean installs and
uninstalls, and the structure of the code and of what it writes to disk.

Five reviews ran, each reading the code and its sources:

- spec 003 against the engine;
- the downloader decision, with spikes against a local server;
- the project against its end goal and philosophy;
- the code as a maintainer would read it;
- installs, uninstalls and the layout on disk.

The claims listed under "Checked in the code" were confirmed by reading the code and the
container directly. The rest cite the reviewer's file and line, or a source.

This file records what was found and what is proposed. The owner decides what is done.

**Outcome (2026-10-02).** The owner accepted the recommendations of decisions 1 to 7, 9 and 10 in
section 9. Decision 8 offered no recommendation and is asked again. The fixes in section 8A landed
on 2026-10-03, each in its own commit with a test that fails without it. Spec 006 (foundations)
and spec 003's core were then drafted in the new one-document format.

## Verdict

**What is sound:**

- Runtimes are isolated, and ports are typed with facets.
- The page has one door into the engine.
- Install markers are written last, and cache commits are atomic.
- The reports are honest: the failed AC8 runs were committed, not hidden.

**What is at risk.** Five days in, there are about 6,300 lines of specs and 6,800 lines of engine
code, and no real model has run yet. Every abstraction has been checked only against test nodes
that do exactly what their manifests say. The next two specs would add more on that same bet.

**What needs fixing in the code:**

- a real process-lifecycle bug: quitting during a run orphans the model's process;
- plumbing duplicated in two or three places, which spec 003 would copy again;
- files on disk with no format version;
- writes that escape the data root;
- no file a person could hand over to explain a failure.

**Spec 003** is not ready to approve. It has four blockers, all fixed by rewording, and its size
is out of proportion to what the first models need. **Decision 2** (our own downloader) holds,
built on `http.client`.

## Checked in the code

- **The run is not offline for Hugging Face libraries, as first written.**
  `engine/src/oneframe/child.py` says hub libraries "are also told they are offline". Nothing in
  the engine or the app sets `HF_HUB_OFFLINE`. The socket guard lets loopback through, and
  `child_env` passes the person's whole environment, tokens included.
- **A Python link escapes the data root.** `uv python install` runs without `--no-bin` (and, on
  Windows, without `--no-registry`). In this container the tests left `~/.local/bin/python3.11`
  pointing into a deleted pytest folder. On Windows each install also registers the Python in
  the registry (PEP 514).
- **Quitting during a run orphans the child.** `Engine.shutdown` stops only an install. Nothing
  sets the job's `exit_with_parent`, so a child loading a model can keep the card until its next
  write.
- **The photo's absolute path ends up in results.** `source.image` writes the path it was given
  into each output's `meta` (`nodes/source.image/node.py`). That carries the person's user name
  into provenance and later exports.
- **The memory model has never been tested against a real model.** The handoff's "estimates
  within 0.1%" comes from `engine/tests/hardware/test.vram/node.py`, whose estimate is "exact by
  construction". It proves the measuring works, not that a formula predicts a real model.
- **The cache key leaves out code and environment.** It is the node's id and version, its
  output-affecting params and its inputs (`engine/src/oneframe/cache.py`). It leaves out the
  node's code and the runtime's lock, so an edited adapter or a torch upgrade serves old results.
- **No `LICENSE` file**, and the README's status still reads "No model nodes yet; those come with
  the runtime manager."

## 1. Sequence and scope

**Where real models are likely to contradict what has been built:**

- **Precision has no speed model.** On compute 6.1, fp16 arithmetic runs at a small fraction of
  the fp32 rate. The fit can pick fp16 to save memory and make a run far slower, with no warning,
  because the slow-device warning fires only when the device changes. The rate per precision and
  compute capability is published by NVIDIA, so it can be data. It does not depend on a card's
  name.
- **The margin is a guess.** It is the larger of 1.5 GiB and 10% of the card, but AC8 measured the
  CUDA context at 88 MB. On a 4 GB card that margin takes 37%. It should be derived again from
  runs of real models.
- **Some models may not fit one formula.** Multi-stage generators (shape model, then decode, then
  texture) have a different peak at each stage. Spec 002's decision 6 already allows a function
  in the node's folder if a formula cannot do it.
- **Spec 003 as decided assumes what is not known yet:**
    - it forces `weights_only` without saying how a node allowlists the objects its checkpoint
      holds;
    - it leaves out libraries that look in `TORCH_HOME` or their own folders;
    - it shapes its views around spec 004's workers, a spec that has not been written.
- **The app cannot yet do several things a first model needs:**
    - load a 200 MB mesh or splat into the sandboxed page: there is no result protocol;
    - let the person pick a photo: there is no file dialog, and today the page sends `graph.run`
      any path it likes;
    - save a recipe: no format is defined.
- **The Improve loop's feasibility is unknown.** Its view synthesisers need 14–24 GB, and most of
  them are Linux-class. Half the product's thesis is the hardest part to run on Windows, and the
  test card cannot verify it.

**A thin vertical slice would remove more risk than anything else on the list:** two real depth
models, downloaded, run from the app, and shown side by side in a viewer.

## 2. Process

**Evidence:**

- Code lands fast: spec 001's ten tasks took under an hour, and spec 002's eleven about forty
  minutes.
- Documents and gates are slow: spec 002 had a draft, a redraft, an amendment and three plan
  reviews before any code, and AC8 took three hardware runs and a reworded criterion.
- Spec 003 is longer than every engine module except two.
- Of its eight decisions, every recommendation was accepted unchanged.

The owner's attention, not the agents' work, is now the bottleneck.

**Proposed:**

- One document per spec, spec and plan together. Aim for no more than 150 lines and 8 criteria,
  with one owner gate. An agent reviews the plan.
- Agents decide reversible choices and log them under "Decisions taken". The owner decides:
    - product behaviour;
    - licences and money;
    - the platform matrix;
    - data formats that are hard to change;
    - the rules themselves.
- A spike lane: time-boxed, no spec, a throwaway branch, ending in a report. Use it for model
  feasibility.
- Versions:
    - the check runs weekly and on `main`, not as a gate on every PR;
    - Dependabot's patch and minor updates merge themselves when CI is green.

**Non-negotiable, unchanged:**

- tests never weakened;
- `main` only through a PR with green CI;
- hardware claims need committed reports;
- no network during a run;
- honest trust labels;
- one door into the page;
- the owner approves product direction and changes to the rules.

## 3. Rules that pull against each other

| Rule | Tension | Sharpened |

it "has to be made on purpose".

## 4. Code and maintainability

Ranked; the file and line references are in the reviewer's report, summarised here.

**High:**

1. **Process lifecycle.**
    - Shutdown stops installs, not runs. The run thread is a daemon, and the child's stdin is not
      watched.
    - The app waits 3 s, then kills `uv`, not Python.
    - Spec 004's idle workers would never die.
2. **One slow request blocks Stop.** The engine answers requests on its input loop, so a large
   `runtimes.remove`, or `nodes.fit` waiting on nvidia-smi, holds up `run.stop`. A reply after
   the app's 60 s timeout reaches the page as an event with no name.
3. **"The network is closed" claims more than it does.** Only Python's `connect` is refused. DNS,
   native clients (`hf_xet` is Rust) and Windows' Proactor asyncio go around it.

**Medium:**

4. **Failures come in four shapes.**
    - There are four `Stopped` classes.
    - Failures are described by `kind`, by `reason` in spaced words, or by a list of `problems`.
    - Error replies carry only a message.
    - The scheduler maps any `ValueError` to `contract`, so an engine bug is blamed on the node.
5. **Plumbing is duplicated:**
    - two data-root defaults, which disagree when `LOCALAPPDATA` is unset;
    - two lists of variables dropped from a child's environment;
    - two ways to kill a process;
    - two ways to write JSON atomically;
    - the scheduler assembled in three places.
6. **No on-disk format has a version and a migration,** except `learned.json`, which is discarded
   and overwritten on a mismatch, so a downgrade destroys newer data.
7. **Nothing guards the data root across processes.**
    - Engine start wipes `cache/tmp`, killing another engine's in-flight commits.
    - The install lock lives inside one process.
    - The benches and the CLI tools use the app's root.
8. **There is no diagnostics file.**
    - Events never reach disk.
    - Per-run child logs are never pruned.
    - uv's output is not kept.
9. **The protocol has no contract.** Nothing checks `ENGINE_METHODS` against the engine's own
   list, and the event names are inconsistent.
10. **Module boundaries:**
    - `memory.py` (1,360 lines) is four modules;
    - `bench_fit.py` hard-codes the runtime `torch` and reads test nodes from the shipped
      package, which breaks "Nothing hard-coded";
    - `cache.py` depends on the child's `Value` type.
11. **Tests:** `test_stop_kills_a_runtime_child` cannot fail on Windows. pyright will fail on the
    first node that imports torch. Spec 005's real-torch tests will need their own cached CI job.
12. **The cache** has no size cap and no eviction.

**Low:**

- **Drift:**
    - `main.js` says every argument is checked;
    - nodes.md misses two runtime reasons;
    - AGENTS.md says "Tests removed" where the guard looks for "Removed";
    - `allow_network` is unused.
- **Tooling:**
    - The test guard notices only deleted names: emptying a test, skipping it or dropping
      parameters passes.
    - The versions job turns unrelated PRs red.
    - The after-edit hook's `ruff --fix` deletes an import added one edit before its use.
    - The docs check proves only that paths exist.

**Before spec 004** (so that it becomes a new executor plus a pool):

- split the child into a once-per-process bootstrap and per-job code, joined by a typed job;
- load node code as a package named for the node, so two nodes' `utils.py` cannot collide;
- give the scheduler an injected executor provider.

## 5. Installs, uninstalls and storage

**What escapes the data root today:**

- uv's Python link in `~/.local/bin`, and its registry entry on Windows;
- Electron's own folders: caches, GPU shader caches and crash dumps under `%APPDATA%` (Roaming),
  which also keys the single-instance lock;
- job folders in `%TEMP%`;
- `__pycache__` written into `nodes/`;
- the engine's environment in the repo.

**Real models will add more:**

- CUDA's JIT cache (Roaming);
- TorchInductor and Triton (temp);
- other libraries' `~/.cache`.

**Other problems:**

- **A dev checkout and an installed app share one root.** Runtimes flip between installed and
  out of date as the locks differ, and the cache serves outputs from code edits.
- **Moving the root breaks runtimes.** They hold absolute paths, but their markers still say
  installed.
- **An uninstaller cannot know what to delete.** electron-builder removes only
  `%APPDATA%\<name>`.
- **Spec 003 keeps the store's location in `settings.json`,** which a standard uninstall deletes,
  so an external store is left without a pointer.
- **Recipes inside the root** contradict "never delete the person's content".
- **Paths:** torch's Windows wheel reaches 212 of 260 characters under the default root, and
  nothing checks a chosen root against OneDrive or FAT32.
- **Run logs and the node cache grow without bound.**

**Proposed layout:**

```
<pointer>  %LOCALAPPDATA%\OneframeLab\location.ini  |  $XDG_CONFIG_HOME/oneframe-lab/location.ini
           (data= and models= when not the default; INI so the uninstaller can read it)
<root>     %LOCALAPPDATA%\OneframeLab  |  $XDG_DATA_HOME/oneframe-lab
  oneframe-root.json        layout format, root id                       full uninstall
  config/settings.json      versioned; preferences only                  standard
  state/                    learned memory, logs (pruned), crashes,      standard
                            locks, reports (listed before removal)
  electron/                 userData (moved out of Roaming)              standard
  runtimes/, uv/            environments, uv cache and Pythons           standard
  cache/                    nodes, jobs (was %TEMP%), session,           standard
                            pycache, runtime caches (hf-home, torch,
                            inductor, triton, cuda); CACHEDIR.TAG
  models/                   the store (or the folder in location.ini)    full, second confirmation
Documents\Oneframe Lab\     recipes and products, chosen by the person   never
```

**Proposed rules for AGENTS.md:**

- **One root.** Everything the app, the engine, a runtime child or a CLI writes goes under the
  data root or its store, in the folder for its class. A footprint test in CI holds this.
- **Versioned formats.** Every on-disk format has a version. A newer file is never overwritten,
  and each change ships with its migration.
- **Safe deletes.** Deletes take the lock, stay inside a folder carrying the root's or the store's
  marker, and never touch the person's content.
- **Separate roots.** Dev and packaged builds never share a root.

## 6. Spec 003, second review

Four blockers, each fixed by rewording; none reverses a decision.

1. **Views have no location or lifecycle.** With hard links, deleting the stored file frees
   nothing while any view still links to it, so "what removing frees" is wrong. Views must live
   under the store root, be derived (rebuilt freely, never counted as content), and lose their
   links when a file is removed. Clearing the read-only attribute on one link clears it on the
   file.
2. **"Redirects only to https" contradicts the loopback test server.**
3. **Nothing names the checkpoint param** when a node has no `weights_by`. Name it once
   (`files_by`), and require it to equal `weights_by` when both exist.
4. **Methods and events are undefined, and slow work blocks the engine.** Download, verify and
   import must be jobs that answer at once. Name `models.stop` and the events, and let refusals
   carry `reason` and `next`.

**Should fix:**

- refuse a store root that cannot make hard links, rather than copy;
- a `files` reason for a conflict and for an offline store;
- the bytes to download are known at the graph's values, not at the fit's;
- the pin tool must be able to re-pin;
- a missing node root blocks "remove unpinned";
- `huggingface_hub` goes in the engine's dev group rather than a third test runtime;
- the trust-store and proxy criteria test what they name;
- give "about a second" a bound, and pick "refused" over "waits";
- torch's zip checkpoints count as pickles;
- import checks space;
- remove takes hashes, never paths.

**Move to the plan:** the 206 and 416 rules, the hashing and rename mechanics, the lock primitive
and the error-code table.

**Cut or defer, without hurting the first models:**

- copied views;
- the third test runtime;
- the proxy matrix;
- the pin tool's digest cross-check and template report;
- import (it comes first if the plan runs long).

## 7. Decision 2, checked again

**The decision holds: our own downloader, built on `http.client`.** A 157-line prototype passed
every resume, stall, Stop and integrity case against a TLS test server.

**What the spikes showed:**

- **Stop.** Closing a response does not unblock a stalled read in urllib, urllib3 or httpx.
  Shutting down the socket unblocks every library, over HTTP and TLS. So Stop needs a watchdog
  whichever library is used. This is the one behaviour still unverified on Windows; spec 003's
  AC3 must pass there.
- **httpx and niquests** ask for gzip by default, which can make CloudFront ignore ranges.
- **huggingface_hub** fails resume across processes, sha256, a fresh redirect per attempt and the
  strict 206 rule.
- **hf_xet** cannot resume after a Stop and computes no sha256. It does open several connections.
- **aria2** is GPL, and its last release was in 2023.
- **curl** adds a binary per OS, with no pinned-size or sha256 check.
- **Electron's downloader** would split the store across two processes and two languages.

**A new finding:** a GitHub release asset's redirect now carries a token that lives 300 s, not
1800 s. Reused after that, it answered `618 jwt:expired`. So an unusual status from a redirect
target means "ask the source again".

**What would change the decision:**

- Windows CI shows the socket shutdown cannot unblock a TLS read. The answer would then be
  non-blocking reads, or a transfer process that Stop kills.
- AC13 shows the per-connection cap on Xet files. Then weigh `hf_xet` against our own parallel
  ranges.
- The engine must speak PAC or NTLM proxies.
- The transport grows past about 600 lines. Then move it to urllib3.

## 8. Proposed actions

**A. Fixes now:** small, each its own commit with a test. All landed; the commit is beside each.

- **Made already:** the runtime torch floor raised to 2.10 (decision 6), `068d6e8`.
- **The run's environment.** `child_env` sets the hub's offline variables and drops tokens and
  endpoints. The child, AGENTS.md and the architecture doc say plainly that the guard stops
  accidents, not malicious code. `8c56e5f`
- **uv.** `uv python install` gets `--no-bin --no-registry`, and `UV_PYTHON_INSTALL_BIN=0` is set
  wherever uv is run. `d209413`
- **Shutdown.** It stops a running graph, and every child exits with its parent. The test asserts
  the interpreter's own pid is gone. `d7f2cd1`
- **The app's engine client** treats any message with an `id` as a reply. `2c9d602`
- **A test asserts that `ENGINE_METHODS`** is a subset of the engine's methods. `2c9d602`
- **A `ContractError`** replaces the blanket `ValueError` mapping. `fd56536`
- **`source.image`** records the photo's file name, not its path. `1654128`
- **The README's status and the handoff's "0.1%" claim** say what was actually shown. `635a6ce`
- **The after-edit hook** runs ruff with `--unfixable F401`. `982c6c8`

**B. Foundations before 003:** structural, best done as one short spec or a planned series.

- one data-root and layout module, used by Python and mirrored in JS, with one table of cases
  tested from both;
- Electron's folders under the root, and a separate root for dev builds;
- job folders, bytecode and runtime caches under the root;
- a version in every on-disk format, atomic writes, and a lock on the data root;
- one failure model, with `kind`, a snake_case `reason`, `message`, `next` and `retry`;
- an event journal on disk, then `npm run diagnose`;
- the cache key gains the node's code hash and the runtime's lock;
- a footprint test in CI.

**C. Spec 003:** reworded for the blockers and cut to its core, or kept whole (decision 2 below).

**D. Later:**

- the first-light spec;
- precision speed by compute capability, with the margin derived again from real runs;
- packaging: guarded deletes, the app removing its own data, one app id, and a clean-VM test.

## 9. Decisions for the owner

Answered on 2026-10-02: 1 to 7, 9 and 10 as recommended. 8 is asked again.

1. **Order.** The fixes, then foundations, then 003 core, then first light (Depth Pro and MoGe-2
   in the app), then SAM 2.1 and a generator, then spec 004, then an Improve-loop spike, then the
   UI, then the rest of 003 and packaging?
2. **Spec 003's scope.** Core now. Import, the store-location setting (with its pointer file and
   location check), the queue, the page's allowlist and planning-time sizes would wait for the UI.
   This changes decisions 4 and 7.
3. **Process.**
    - Spec and plan together, with one gate and about 150 lines.
    - Agents decide reversible choices and log them.
    - A spike lane.
    - The versions check off the PR gate, with automatic minor updates.
4. **Foundations:** as one short spec, or as a series of fixes?
5. **Version policy for runtimes:** the newest the family supports, and an older torch line per
   build where a newer one drops cards.
6. **Evidence:** do reports from rented GPUs count, and does the catalogue show verification
   labels?
7. **The platform matrix for v1:** Windows and Linux on x86-64, NVIDIA and the CPU. Are macOS, AMD
   and Intel out? Is WSL allowed for Linux-only nodes?
8. **A public release:**
    - If yes: a licence (MIT?), signing, a cleared name, user docs and an accessibility baseline.
    - If no: drop signing and the updater from the roadmap.
9. **The first slice:** Depth Pro and MoGe-2? A node allowlists its checkpoint's objects with
   `add_safe_globals` in its own folder, and never turns `weights_only` off.
10. **Storage rules:** adopt the four AGENTS.md rules in section 5, and the layout as the target.
