# Review of the project before first light (2026-10-12)

The owner asked, as spec 005 was about to be drafted, to look at the work again against what the
project is for, and to check that it is not drifting from its design, and that it stays
maintainable and modular.

Three reads:

- **The code**, by an agent, every finding with its file and line. The findings used below were
  checked again by hand.
- **The process, the docs and the tests**, by an agent, from the git history, a full test run and
  CI's last 100 runs.
- **The objective and the landscape**, from the handoff, the [review of 2026-10-02](2026-10-02.md)
  and a web search. ComfyUI's state comes from secondary reports; its own blog cannot be reached
  from the cloud container.

## Verdict

1. **The design still fits the objective.** Nodes as data, typed facets, one environment per
   model family, fit before load, one data root and honest labels are all in the code and hold.
   The landscape sharpens the case for one of them (below). Nothing found calls for a change of
   direction.
2. **The project is lopsided.** In two weeks it has grown to:
    - 11.6k lines of engine and 11.1k of tests;
    - 11.7k lines of specs, reports, reviews and docs;
    - 0.9k lines of app and 98 lines of nodes.

   No model has run, and the page lists nodes. The 2026-10-02 review agreed "one thin slice
   before more infrastructure". Its two prerequisites (specs 006 and 003) each came out larger
   than their specs said they would. The slice is still ahead.
3. **Four things in the code would make the first model nodes wrong or harder.** They are cheap
   while there are no model nodes, and expensive after.
4. **The process change of 2026-10-02 did not make specs or the handoff shorter.** Code lands in
   hours; documents and waits take days.

## 1. Against the objective

Most of what is built will be used. The trouble is that it was built before anything tested it
against a real model:

- no memory model has been measured on a real model;
- 7 of the engine's 19 methods cannot be reached from the page;
- about 300 lines for runtime sources and compiled extensions have no runtime that uses them yet.

The risks that would change the design most are the ones not yet retired:

- **Real models on Windows with Python 3.14** (step 3). MoGe-3's code imports FlexGEMM, which
  is built on Triton, and Triton 3.8.0 on PyPI has Linux wheels only.
- **Compiled extensions** (step 4).
- **The Improve loop**, and whether it needs WSL (step 6). If a runtime has to live in WSL, it
  touches the runtime manager, the locks (Windows and Linux locks across the boundary), the data
  root's paths and the child's environment. That answer is five steps away, and a spike can get
  it in days on a rented GPU (a rented machine's report counts).

**Build or adopt.** The 2026-10-02 review noted that this decision was never written down. It is
more pressing now:

- **ComfyUI has moved into this space.** Secondary reports say:
    - native TRELLIS.2 and Pixal3D image-to-3D, with MoGe depth, since August 2026;
    - a native Gaussian-splat type with preview and manipulation nodes in v0.23.0 (June 2026);
    - native splat generation (TripoSplat).
- **It still runs every node in one shared Python environment.** Its own docs on dependencies
  advise loosening pins when node packs conflict, and per-pack isolation is still a plan.
- **What only this design does:**
    - one environment per model family, behind a process boundary;
    - fit before load on any card, from no GPU up;
    - typed geometry (facets, so disparity never becomes metric silently) and trust labels;
    - no network during a run;
    - a product shaped around two loops, not a general editor.
- **What ComfyUI does better, and should not be competed with:** a general graph editor, and
  breadth of nodes. ComfyUI is GPL-3.0 and this app is MIT, so its code can be read to learn how
  a model is called, but not copied.

**Recommendation:** keep building, write the decision down with the differentiators above, and
narrow step 7. The workspace becomes the two loops (a photo in, variants side by side, compare,
improve), with recipes chosen rather than drawn. A general graph editor comes later, or never.

## 2. Rules under pressure

- **There is no home for a pipeline.** "Nothing hard-coded" allows no code outside a node's
  folder to name a pipeline, and there is no recipe format. So the page cannot build "photo →
  Depth Pro → points" without naming nodes, unless a graph editor comes first. `convert.depth_to_points`
  takes two inputs, so the planner cannot insert it on its own.
    - **Proposed:** recipes as data, found by looking like nodes, checked by `plan()`.
    - They need room for the page's own fields; `Graph.from_json` drops unknown keys today.
- **The page chooses the photo's path.** The door passes `graph.run`'s params through unchecked.
  Once the page can read results, a compromised page could read any image on disk.
    - **Proposed:** a dialog in the main process hands the page an opaque token.
    - Results are served by their value's key through a protocol, never by path.
    - Today every `node.done` carries absolute paths.
- **An old violation:** `oneframe/bench_fit.py` names the runtime `torch` six times, and ships
  spec 002's AC8 scenario inside the package, with a path to `engine/tests/hardware`. This has
  been open since 2026-10-02, and no test checks the rule.
- **Rules growing into exception lists.** "One data root" in AGENTS.md is 190 words with seven
  exceptions, edited in seven commits. It is several rules in one bullet.

## 3. Code: what to fix before the first model node

**Wrong today, and cheap now:**

1. **A node's imports can load the engine's own modules.**
    - The child starts as `python -u child.py` (`oneframe/executors.py`), so `engine/src/oneframe`
      comes first on its path.
    - Inside a runtime, `import models`, `graph`, `errors`, `files` or `layout` therefore loads
      the engine's module, and pinned sources come after it.
    - The node's folder also comes first, so a helper called `utils` hides a package of that name.
    - **Fix:** start the child with `-P`, and load node code as a package named for the node (on
      the "before spec 004" list already).
2. **A node cannot fail with kind `node`.**
    - `NodeFailed` lives in the child script's `__main__`, which node code cannot import.
    - `ctx.check_stop()` does nothing in a child; Stop kills the process. `docs/nodes.md` says it
      raises.
    - `ctx.job`, `outputs`, `ways`, `out_dir` and `node` are public but undocumented, and `ctx`
      has no type.
    - **Fix:** a small node API module, standard library only, holding `Value`, the context,
      `Stopped` and `NodeFailed`. `child.py` imports it, so `errors.py`, `cache.py` and
      `scheduler.py` stop importing the child script.
3. **Every node would be rewritten for spec 004.**
    - The contract is `run(ctx)`, and the child forgets a node's modules before each job.
    - **Proposed:** decide the shape in spec 005: an optional `load(ctx)` that returns state, then
      `run(ctx, state)`. One process per run simply calls both, and spec 004 keeps the state.
4. **`models:pin` writes `node.json` in a `finally`, with no atomic write.** Ctrl+C during the
   write leaves a truncated manifest.

**Debt to pay when the code is next touched** (none blocks first light):

- **Five large modules hold more than one module each:**
    - `oneframe/memory.py` (1,430 lines) is five: the model and its parser, settings, devices and
      the estimate, the fit, and the learned store.
    - `oneframe/runtimes.py` (1,066) is three.
    - `oneframe/child.py` has five concerns.
    - `oneframe/manifest.py` imports all of memory, the learned store and settings included, just
      to parse a manifest.
- **Duplicated mechanisms:**
    - two lists of variables kept from children, differing in members and in case;
    - three ways to kill a process, and three start-and-read loops;
    - `NO_WINDOW` three times;
    - a file's sha256 computed in five places;
    - two downloaders: runtime sources still use urllib with no resume (`oneframe/archives.py`);
    - a job's dict built in three places.
- **The download transport passed its own tripwire.** Spec 003's research said to switch to
  urllib3 if `oneframe/models/transport.py` passed about 600 lines; it is 754.
    - **Recommendation:** keep it. It passed the real hosts in AC8.
    - Record that the tripwire fired and why the transport is kept, add nothing more to it, and
      move runtime sources onto it.
- **The longest functions:**
    - the runtime `install` (179 lines, three nested closures);
    - the scheduler's `_attempt` (123 lines, 9 arguments);
    - the manifest's `parse` (118 lines).

  `Scheduler.__init__` takes 15 parameters, and the executor cannot be swapped (needed by spec
  004).

**Specs.**

- Neither spec written after 2026-10-02 met the 150-line aim, even at approval.
- The limit of eight criteria was kept only by nesting checks under them.
- The single gate did not hold either:
    - spec 003 was amended after its approval;
    - spec 006 had four owner rulings after its approval.
- What inflated them:
    - an implementation log under "Decisions taken": 32% of spec 003, including retry and stall
      values that specs/README.md says belong in code;
    - mechanisms written into the requirements;
    - status lines that are lists of PRs.

**Where the time went.**

- Spec 006 was implemented in 46 minutes.
- Spec 003's code and tests landed in 11 commits over 2 hours 50 minutes, after 6.6 days without
  a commit, between its amendment and its implementation.
- Its spec.md was written +1,505 and −1,084 lines to end at 421.
- 42% of all commits change only prose.
- As in the last review, the owner's attention is the bottleneck. Every extra line of spec spends
  it.

**The handoff** is 292 lines:

- current state and next steps take about 40 of them;
- it carries 39 open items, three of them untracked:
    - the per-node verification label accepted on 2026-10-02;
    - licence pages opening in the browser;
    - the transport tripwire.
- some of it is stale:
    - "uv's lock from the npm tools" is listed as a gap, though `scripts/tool.js` closed it;
    - "on this branch" in the order table;
    - the list of checks.
- 5 of 22 PRs changed only the handoff.

**Tests and CI.**

- All 561 engine tests pass in 61 s.
- Weak spots:
    - The test guard cannot see what it most needs to: an emptied test body, a skip mark, or any
      of the 139 parametrized cases.
    - A test that checks nothing: `tests/app/layout.test.js`'s "the command-line tools write no
      bytecode" has matched no script since the tools moved to `scripts/tool.js`.
    - Two flaky tests: the footprint test, and a Windows Stop hang.
    - Test helpers duplicated across files.
    - Nine assertions that bound wall-clock time.
- `.github/workflows/checks.yml` runs on a push to every branch and on every pull request, so each
  PR commit runs twice. It has no timeouts.
- CI has no Electron launch and no job with real torch. Review item 4.11 is still open, and first
  light needs both.

## 5. Recommendations, in order

**A small fix PR before spec 005's code.** No spec; one commit each, each with a test:

1. Start the child with `-P`, and make `NodeFailed` and `Stopped` importable from a node API
   module. Make `docs/nodes.md` say what `check_stop` does in a child.
2. Make `models:pin` write the manifest atomically.
3. Make the dead app test check the launcher instead.
4. CI: run on push only for `main`, with a concurrency group and `timeout-minutes`.

**In spec 005 (first light), held to about 150 lines:**

5. Recipes as data, with the page's own fields kept.
6. The photo dialog's token, and the result protocol by value key.
7. The `load` and `run` split, so the first model nodes are written once.
8. A CI job with real torch on the processor.
9. Decisions logged one line each, and the build log kept in the PR.

**In parallel:**

10. The Improve-loop spike (step 6), started now on a rented GPU, since its answer can reshape the
    runtimes and the data root.

**When the code is next touched:**

- the module splits;
- the duplicated mechanisms;
- the executor provider (already "before spec 004");
- the test guard reading collected test IDs and skip marks.

## 6. Decisions for the owner

1. **Build or adopt:** keep building, with the differentiators in section 1 written into
   architecture.md? And narrow step 7 to the two loops, with no general graph editor in v1?
2. **The Improve-loop spike now,** in parallel with first light, on a rented GPU? That costs
   money; the 1070 cannot run the view synthesisers.
3. **Process** (these are rules):
    - the docs check fails a spec over 200 lines;
    - "Decisions taken" holds one line per decision;
    - the handoff is cut to about 80 lines (state, next, blockers), with parked items moved to a
      roadmap document;
    - "One data root" is split into short rules, with its exceptions kept as data that the
      footprint test reads.
4. **Order:** the fix PR (section 5, items 1 to 4) before spec 005's draft? It changes no
   behaviour a person sees.
