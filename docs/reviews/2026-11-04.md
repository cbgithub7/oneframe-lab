# Review of the project toward its end (2026-11-04)

The owner asked, once step 3's specs were drafted, for a review in the manner of the
[first one](2026-10-02.md), looking past the next step to the end of the project: whether the work
still serves the objective and its design philosophy, and whether it will stay maintainable and
modular through the steps left.

Four reviews ran, each reading the code and docs, none editing them:

- the four step-3 drafts against the code (their findings went into the drafts; section 4);
- the architecture against the end goal, step by step to packaging;
- the code as a maintainer will live with it;
- the process, the rules and the philosophy, against what was delivered.

The claims under "Checked in the code" were confirmed directly. The rest cite their file and line,
or are marked as the reviewer's reasoning. The owner decides what is done.

**Outcome (2026-11-04).** The owner took every decision in section 6 as recommended, and answered
every open question of the step-3 specs as recommended; the spike (decision 2) comes first. 017's
third question, running past a failure, became 015's requirement 6. The rule changes (decisions 4 to
6) come as one PR for the owner to read; protecting `main` (decision 8) is a setting only the owner
can change on GitHub.

## Verdict

**What is sound, and must be kept:**

- **The differentiators are intact:** one environment per model family behind a process
  boundary, the fit to memory on any card, typed facets with trust, no network during a run.
- **The seams the end goal needs exist:**
    - the `Executors` injection carries spec 004's workers and a WSL executor;
    - the content-keyed cache, with `Value.key`, carries results by key, side by side and "compared
      against the first" with no new identity scheme;
    - the runtime plan, built from what the card reports, refuses a model where it cannot run.
- **The 2026-10-12 debt is paid.** No function over 100 lines but `graph.plan`, no import cycle,
  one home each for processes, the child's environment, hashing and the transport.
- Failures are declared once, checked against the docs, and reach the page as values.
- The door is testable without Electron. The test guard costs about a second.

**What is wrong:**

- **Five weeks in, a person can do nothing new.** `npm start` shows the page of 2026-10-04, a list
  of two nodes. Since 2026-10-05, the page and the nodes changed by 8 lines; the engine by about
  15,800 and its tests by about 11,000. The two earlier reviews each said to cut one thin slice
  before more infrastructure; eight clean-up specs came next.
- **The engine–page protocol is prose.** About 43 event names are built as dict literals in 51
  places. No schema or test holds them to architecture.md, and the page's types are `any`. Spec
  017's page will be written against prose.
- **Today's graph model is too narrow for the end goal.** A run is the whole graph, one at a time,
  and stops at its first failure. A value is one file, and no param holds structured data. A world
  from one image needs N masks, then N meshes, then N poses; and clicks on the page.
- **The rules and the docs have grown past "short and true".** `AGENTS.md` is 1,660 words. The
  handoff is 108 lines, against the 80 the owner set, and the README's status is a month old.

**The risk:** the project keeps the shape of a careful engine with no product. Every remaining
risk that would change the design (real models on Windows, the Improve loop, compiled extensions)
is found only by running real models. The order below puts that first.

## Checked in the code

- `cache.py:167,174,181` and `archives.py:100` delete with `shutil.rmtree(ignore_errors=True)`, not
  `files.remove_tree`: on Windows, a read-only file is left behind without a word.
- `.claude/hooks/before-stop.js:57-58` fingerprints `git status --porcelain` and `git diff HEAD`.
  Neither holds what an untracked file contains, so editing a new file after one passing check is
  not checked again before the turn ends.
- `contracts/port-types.json`'s comment says every value carries its source image's id; no code
  sets one.
- `manifest.py:38` holds the category `"test"`, which only the test suite uses.
- The workflows hard-code uv `0.13.5` three times, and `npm run versions` does not compare them.
- The scheduler ends a run at its first failed step (`scheduler.py:233,243`).
- `bench_fit.measure` builds a graph of one node with no edges (`bench_fit.py:93`), so it cannot
  measure a node that needs an input.

## 1. Against the end goal

Steps 3 to 8, and "a world from one image", walked against today's design.

**Carries well:** the executor seam (steps 5 and 6), the content-keyed cache (steps 6 and 7), one
runtime per family planned from the card (steps 4 and 6), trust inheritance for synthetic views
(step 6), and the page's `page` fields and one `connect()` rule that spec 015 adds (step 7).

**Will need reshaping, and when:**

1. **A run that meets a failure stops** every branch, even the ones that do not depend on the
   failed step. In 017's graph, a missing Depth Pro runtime would also stop MoGe. *In 017* (its
   open question 3): keep running the branches that do not depend on the failed step.
2. **One run at a time, always the whole graph.** SAM's clicks (step 4) will collide with long
   Improve-loop runs (step 6). *Before step 4:* runs up to a chosen node, and a slot per device.
3. **No collections, no "for each".** One photo to N objects needs a set carrier (a folder, as
   `ViewSet` already is) and a "for each" in the recipe. *Before step 4.*
4. **The page cannot author data.** `PARAM_TYPES` has no structured type for clicks, camera-path
   keys or an object's placement. *Before step 4:* a `json` param checked against a port type.
5. **Port facets for the scene types.** Every value must carry every facet its type has
   (`_check_outputs`). A facet added to `Mesh`, `GaussianSplat` or `Pose` after nodes make them
   would break every producer. The cache key leaves out `port-types.json`, so a contract change
   leaves old entries that then fail as `edge`. *Before step 4:* the contract's digest in the key,
   scale and frame facets on the scene types, and an `Audio` type.
6. **The cache has no cap and no record of use,** and every update orphans its entries for good.
   The Improve loop's view sets grow fast. *Step 6, not 8:* last use recorded, a cap, and nothing a
   saved graph names collected.
7. **Spec 004's seam is thinner than it looks.** `Executors` has no lifecycle and no memory
   accounting. The fit reads free memory from nvidia-smi, so a warm worker's model counts as taken,
   not as memory the engine could free. A runtime remove does not know a warm worker holds the
   runtime's folder. *In 004:* `held_mb`, `release` and `close` on the protocol, and the fit counts
   held memory as free once released.
8. **WSL,** if the spike says so. A job carries Windows paths, the locks assume one system, and the
   plan cannot say "Linux, through WSL". *The spike should measure:* loading weights across `/mnt/c`,
   and locks across the boundary.
9. **Compiled extensions.** A `required` extension blocks its runtime everywhere. Prebuilt wheels
   multiply by Python, torch, CUDA and system, and each new torch means rebuilding them. *At step
   4's start:* the owner decides where wheels are built and hosted.
10. **Packaging** starts the engine with `uv run --project <repo>/engine`, there is no folder for a
    person's own nodes under the root, and a changed lock reinstalls a runtime of several GB. *Step
    8's spec* covers all three.

**Over-built for now:** a FlexGEMM build nothing here can test (taken out of 005), and the memory
model's language (upgrades, per-capability times, offload), which has outrun any measurement:
grow it only from 005's numbers.

## 2. Code

1. **Declare the protocol** as failures are declared: `contracts/protocol.json` (each event and
   result with its fields), a test holding the engine's events and architecture.md to it, and the
   page's types generated from it. Tests that assert exact event lists (about ten) should assert
   order instead, so that a new event does not break them. *Before 017's run view.*
2. **Vocabularies the page also needs live in the engine:** `CATEGORIES`, `PARAM_TYPES`, `DEVICES`,
   with `"cuda"` and `"cpu"` spelled 40 times in 15 modules. A sound node needs an engine edit for
   its category. *Before step 4:* categories and param types in `contracts/`, devices named once,
   and `"test"` out of the shipped list.
3. **The page needs a bundler sooner than 017 thinks.** three's add-ons (OrbitControls, for linked
   cameras) import the bare name `three`. That needs an import map, which `script-src 'self'` allows
   only by hash, or a bundler. *In 017:* esbuild, pinned (step 8 needs it anyway), keeping JSDoc and
   tsc. Not verified here: three is not installed.
4. **One tsconfig gives every environment both DOM and Node types,** so renderer code may import
   `node:fs` and pass. *In 017:* one config per environment, and the renderer's imports restricted.
5. **Duplicated mechanisms that remain:** four canonical-JSON sha256s (`memory/model.py:473`,
   `memory/estimate.py:59`, `cache.py:120`, `manifest.py:397`), 13 hand-rolled JSON reads beside
   `reading.read_object`, the `rmtree` calls above, and the node lookup twice in `server.py`.
   *When next touched,* each into its one home.
6. **`scheduler.py` will grow in three directions:** the step loop, the fit and oom policy, and the
   output contract check. *Before 017's open question 3 and spec 004:* the contract check into its
   own module.
7. **A node's Python target is not tied to its runtime.** ruff targets 3.15 everywhere but engine
   paths, and pyright names `runtimes/torch` by hand. A node for a runtime on 3.13 would be
   reformatted into syntax it cannot run. *In 005:* derive both from each node's `run.runtime`, or
   check them.
8. **The stop hook** runs about 100 s on every turn that changed something, and will slow with the
   tests. A fast tier for the hook, the full run in CI, once it hurts.
9. **About 15 tests patch private internals** (`transport._write`, `Jobs._download`, `ctx._done`),
   which will slow refactors. Seams in their place when the code is next touched.
10. **Names read as a house dialect** (`found`, `again`, `served`, `say`, `_said_oom`), and so does
    the prose ("an ending sent after its place is free"). A glossary of about 15 terms in
    architecture.md helps a newcomer more than renaming.

## 3. Process, rules and philosophy

1. **The owner's attention sets the pace, not the code.** Specs 008 to 012 were each implemented in
   a day; the gaps lie around approvals. Six clean-up specs waited five days to be approved again
   after wording changes from `/code-review`. Every spec takes a second PR to say it is done, and
   about 11 of 53 PRs did only that.
2. **005 holds a spike's questions:** Depth Pro on numpy 2, MoGe-3's import with a stand-in, MoGe
   on Windows and on Pascal. Rule 3's own example of a spike is "does this model run on Windows".
   A day or two on the 1070 in a throwaway environment answers them before 005 is approved, and
   005 then states facts, not risks.
3. **The spec limits are filled to the line.** Specs 008, 010, 011 and 014 are exactly 200 lines,
   and mechanisms still appear in specs. Step 3 is four specs and about 600 lines, where the
   review of 2026-10-12 asked for about 150. The split is sound on dependencies, though the cap
   drove it as much as the design did.
4. **A new model node needs no spec.** A node that changes no engine, app or contract code is data
   and node code. It could ship as one PR: manifest, code, a CPU smoke test and a `bench:fit`
   report. A new runtime family or a licence question still needs a spec.
5. **`AGENTS.md`**:
    - **Rules that earn their keep,** each held by a test: light engine, nothing hard-coded, one
      door, the test guard, no network during a run, honest labels.
    - **Rules grown long:** "one data root" (its exceptions are data now, its text still about 110
      words) and "any card" (now also the platform matrix and WSL).
    - **Rules nothing checks:** "one way to do each thing" is judged only in review.
    - **Missing for the page:** its security as a standing rule (the CSP, no remote code, what the
      value protocol may serve), accessibility, and performance budgets (time to a first result,
      points drawn).
    - The commands (about 35 lines) belong in the README.
6. **Docs drift where a newcomer starts:** the README's status, the handoff's dates and length,
   and its state table, which restates each spec's mechanisms. architecture.md and nodes.md match
   the code where checked.
7. **Strictness that costs more than it protects:** the footprint test watching the real profile
   (flaky on Windows twice), and "latest stable" with no grace for a new Python minor, which cost a
   day of bumps for an engine that runs no model code.

## 4. What this review changed in step 3's specs

The draft review's findings were taken into the drafts (commit `076ad14`); the architecture
review's simpler designs too, as reversible choices, each logged in its spec:

- **005:** no FlexGEMM build until a card of compute 8.0 or newer reports; a stand-in in every
  build, so no new runtime mechanism. `bench:fit --graph` measures a node with real inputs. The
  label for MoGe-3's missing refinement goes in the node's own `meta`, because the engine writes
  `made_with`. The CI weights are cached once for both systems.
- **015:** graphs are found as files, a saved graph shadows a shipped one of its name, and
  `graph`/`newer_format` is a new failure reason. `fits` answers `depends` for a facet decided at
  run time, and `no` for an edge that would close a cycle.
- **016:** a photo is imported into the root by its sha256, and a `file` param holds that hash, from
  any caller. A saved graph then holds no path, the door reads no graph, and `nodes.fit` can no
  longer probe the disk. Every string the page receives is scrubbed of the root, the repo and the
  home folder. A stop cancels a queued request of its kind.
- **017:** the whole rule for what a failure offers; the person's own node and graph folders
  (`ONEFRAME_NODES`, `ONEFRAME_GRAPHS`), which the end-to-end test uses too; `npm run e2e`.

## 5. Recommendations, in order

1. **First light before anything else.** Infrastructure and clean-up wait until 017's run on the
   1070 passes, except what blocks it, and the hook fix below.
2. **A local spike on the 1070, one or two days,** before 005 is approved: a throwaway environment,
   Depth Pro, MoGe-2 and MoGe-3 (with a stand-in for FlexGEMM) once each, seconds and peak VRAM.
3. **Approve 005 on the spike's facts, then 015 to 017 as one decision.** Into them before code:
   the protocol contract (into 016) and esbuild with one tsconfig per environment (into 017).
4. **Small fixes now, no spec, one commit each with a test:**
    - the stop hook fingerprints untracked files' contents;
    - `npm run versions` checks the workflows' uv pin.
5. **After first light, before step 4: a "graph model 2" spec.** Collections and "for each", runs up
   to a node and a slot per device, a structured param, the contract's digest in the cache key,
   scene facets and `Audio`, the vocabularies in `contracts/`, and the source image's id carried or
   the claim removed.
6. **Process, from now:**
    - approve again only when requirements, criteria or open questions change;
    - a spec is marked done in the PR that implements it;
    - the light path for model nodes;
    - `AGENTS.md` at one or two lines per rule, each naming its test, the commands in the README,
      and the three page rules;
    - the handoff at about 80 lines, and a glossary in architecture.md.
7. **When the code is next touched:** the duplicated mechanisms in section 2.5, the scheduler's
   contract check, the tests' private patches.
