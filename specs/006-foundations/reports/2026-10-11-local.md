## Two attempts, and why

**The first attempt ran inside the Claude desktop app and does not count for steps 2, 3 and 5.**
Claude desktop on this machine is an MSIX package. Every process a Code-tab session starts (its
shell, `npm start`, uv, the engine) inherits the package's container. Windows silently redirects a
*new* folder under `AppData` to the package's private storage,
`%LOCALAPPDATA%\Packages\Claude_pzs8sxrjxfjjc\LocalCache\Local\`. A folder that already exists,
such as the old root or Electron's download cache, is written in place. From inside, `dir`, `ls`
and `reg query` all show the merged view, so nothing looked wrong until `npm run diagnose`, which
resolves the root's path, printed the package path. HKCU registry writes from a package are
virtualized the same way. So the first attempt's root, with its torch runtime (136.3 s, 4,360 MB),
landed where only Claude's processes see it, and its step 5 could not have seen a stray write.
Step 4 was valid there too: 0 mentions of the user name.

**The second attempt** ran the same commands from a script the owner started in Windows Terminal
from the Start menu. Its process chain was `powershell.exe <- pwsh.exe <- WindowsTerminal.exe <-
explorer.exe`, outside any package. There `diagnose` printed `%LOCALAPPDATA%\OneframeLab-dev`
itself. The verdict above is from this attempt.

The checks below ran inside the container. That is fine for them, except that AC2's Windows
footprint test then sees the same merged view; CI's Windows job runs it outside any package.

## Other observations

- **Electron fetched its binary on the first `npm start`** ("Downloading Electron binary…", the
  44.4.5 zip, 158 MB). The `electron` package has no install script and downloads on first run,
  into its own cache `%LOCALAPPDATA%\electron\Cache` (here from 2024, so not new at the top level),
  then unpacks into `node_modules`. This is the dev tool installing itself, not the app writing.
  On a fresh machine it would be a new top-level folder in `%LOCALAPPDATA%` during development,
  and spec 006's exceptions do not name it. The second attempt downloaded nothing.
- **Two stale `HKCU\Software\Python\Astral` keys predate spec 006.** Today's runs left the hive
  unchanged. `CPython3.14.7` points into the old root's `uv\python`, so it will dangle once step 6
  deletes that root, unless `uv python uninstall 3.14.7` runs first with `UV_PYTHON_INSTALL_DIR`
  set to that folder. `CPython3.11.16` points into a pytest temporary folder from 2026-10-01
  (`pytest-411\uv-home0`), from a test run before spec 006 made installs leave the registry alone.
- **No bytecode was written into the checkout.** The `*.pyc` files under `engine/src`, `nodes` and
  `runtimes` are all from 2026-10-01 or earlier.
- The first attempt's root (about 4.4 GB) is still in Claude's package storage. Anything started
  from Claude would keep using it instead of the real root, so the owner may delete it.
