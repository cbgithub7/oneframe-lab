## The README's questions

1. **Do both families install on Windows with Python 3.14 and torch 2.14.0's `cu126` build, from
   their GitHub code, with no FlexGEMM, gradio or upstream torch index?** Yes. All four
   environments built from the locks with CPython 3.14.7: `cu126` in 30 s (Depth Pro, 4.2 GB) and
   28 s (MoGe, 4.4 GB), torch coming from the data root's uv cache; `cpu` in 45 s (0.6 GB) and
   41 s (0.8 GB). uv raised no os error 32 from outside the package.
2. **Does Depth Pro run on numpy 2?** Yes: numpy 2.5.4, real weights, on the card at both
   precisions and on the processor.
3. **Does MoGe-3 load and run without its refiner, with the stand-in and `refine_steps=0`? Does
   MoGe-2 run from the same package?** Yes to both, on compute 6.1 and on the processor. Without
   its refiner MoGe-3 is MoGe-2's size: 330.9 M parameters and 1,327 MB on the card for each, and
   the same seconds within noise.
4. **Do the weights load with `weights_only` forced, from the model store, with every network
   connection refused?** Yes. All 13 runs loaded the pinned file by its sha256 from the store, with
   `TORCH_FORCE_WEIGHTS_ONLY_LOAD=1` and Python-level connections refused; none failed, so none
   needed a connection.
5. **Seconds, memory and sane depths:** the tables above. Each output's depth is in metres and
   finite where valid: Depth Pro 100 % finite, 1.35 to 16.4 m, median 3.6 m, focal 2,074 px (70°
   across); MoGe-2 and MoGe-3 87.3 to 87.4 % valid (the sky masked), about 2.5 to 146 m, median 6.8
   to 7.5 m, 77° to 82° across. On the same model and setting, the card's and the processor's
   minimum, median and maximum depths agree within a millimetre. A look at the depth maps beside the photo: all three have the people, the bus and
   both walls receding; MoGe puts the corridor's far end at about 125 to 145 m, Depth Pro at most
   16 m with the sky no farther than the walls. One photo, so a note, not a verdict on a model.

## Findings

1. **Depth Pro at fp32 needs more than the 1070 has, and Windows did not refuse it.** Its run
   peaked at 8,797 MB allocated (3,636 weights + 5,161 working) on an 8,192 MB card that had 575 MB
   in use before the run, with no out-of-memory error. Allocations past the card's own memory can
   only have been backed by system memory (the WDDM driver's shared memory; its fallback setting
   was not read). That run took 19.5 to 20.8 s against fp16's 5.6 to 5.9 s. fp16's reserve,
   9,458 MB, also passed the card's size while its allocated peak (5,002 MB) did not. The spike
   sets no cap; under spec 002's cap such an overrun is refused, not slowed. So on Windows the cap
   is what keeps a fit honest. Whether Depth Pro at fp16 fits under the cap on this card is AC6's
   to show.
2. **Depth Pro's fp16 load peaks at fp32's size:** 3,641 MB allocated during the load against
   1,826 MB once loaded, because the weights are read in fp32 and then cast. The fit before a load
   has to allow the fp32 size for an fp16 load.
3. **MoGe's fp16 gains nothing on compute 6.1:** the same seconds as fp32, and about 200 MB *more*
   allocated at level 9 (2,681 and 2,697 against 2,483 and 2,498 MB), since upstream's fp16 is
   autocast over fp32 weights. A memory model must not treat it as a saving.
4. **Process memory was not measured on Windows.** Every row's `peak_rss_mb` is `null`:
   `run_model.py` calls `GetProcessMemoryInfo` through untyped `ctypes`, so the current-process
   handle (−1) goes as a 32-bit int and the call fails with error 6 (invalid handle). The same call
   typed with `HANDLE` reads the peak (checked here with the spike's own interpreter). The engine's
   `oneframe/node/usage.py` already types it correctly; the spike carried a second copy of that
   helper. Not changed here (a local session verifies); a rerun of step 3 after a fix would fill
   the column.
5. **Times beside the inference:** imports 6 to 7 s (15.5 s the first, cold); loads 11 to 15 s for
   MoGe and 28 to 37 s for Depth Pro; MoGe's first inference on the card 3.5 to 4.3 s against 0.4
   to 1.3 s steady. Each card row's process took 28 to 97 s, most of it before the first inference:
   spec 004's case for keeping models loaded.
6. **On the processor** (Intel Core i7-4770K, 4 cores): Depth Pro about 99 s an inference and 236 s
   a process; MoGe-2 and MoGe-3 at level 0, 9 to 12.5 s an inference and 44 to 46 s a process.

## What 005 should change

- Keep the decisions the spike backs: Depth Pro on `numpy>=2`; the `flex_gemm` stand-in and
  MoGe-3 at `refine_steps=0`, which run on compute 6.1 on Windows; MoGe-2 and MoGe-3 in one
  runtime. Two MoGe nodes cost nothing more to run than one.
- Depth Pro's memory model: working memory about 5.2 GB at fp32 and 3.2 GB at fp16 at this photo
  size, and the load's peak at the fp32 size whatever the precision. Where fp32 does not fit, as on
  this card, the fit chooses fp16 or the processor from these figures, never from the card's name.
- MoGe's memory model: working memory at fp32 about 0.55 to 0.61, 0.87 to 0.88 and 1.16 to 1.17 GB
  at levels 0, 5 and 9; fp16 is fp32's weights plus more working memory, not less.
- The processor's memory: still unmeasured on Windows (finding 4). The engine's own helper reads
  it correctly; whether `bench:fit` reports it for these nodes is AC6's to show.
