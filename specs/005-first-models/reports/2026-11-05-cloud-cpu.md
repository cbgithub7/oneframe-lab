# Spec 005's nodes on a cloud session's processor, with random weights

2026-11-05 · branch `claude/eloquent-archimedes-74uqi8`, task 6 · a cloud session: no card, no
Hugging Face, no Apple CDN

Each of the three nodes, run through the engine with `npm run bench:fit -- --graph` on the
processor, to show that its `load` and `run` work end to end, and to measure the system memory a
run takes there, which the spike could not read on Windows (its finding 4). Not a hardware claim:
there is no card here, and the weights are random.

The estimate is the processor's, from the manifests' figures before this report (weights plus
working memory, both from [the spike](2026-11-03-spike.md)); the peak is how far the run's process
grew (`peak_ram_mb`), which on the processor is also its system peak. Each row is one process: the
seconds hold the imports, the load and one inference, and the first run of each node read its
weights from a cold disk.

## What it shows

- **Every node loads and runs through the engine:** the store's file through `ctx.file`, under the
  engine's forced `weights_only` and with connections refused, every output checked against its
  port by the scheduler (status `done`).
- **Depth Pro's load holds no second copy:** built on torch's meta device, the file's fp16 tensors
  assigned, cast to fp32 on the processor; the whole run at fp32 peaked under its estimate.
- **MoGe's load holds its weights twice:** the checkpoint read beside the network upstream builds
  at random, about 2 × 1,392 MB, which at level 0 is more than the run itself. The manifests' system
  figure is now that: twice the weights and 178 MB, the larger of the two level-0 peaks less
  2 × 1,392. Their processor estimate becomes 2,962 MB at every level: a ratio of 1.00 at level 0
  and 1.07 at level 9 against these peaks.
- **On the processor, MoGe at level 9 takes about 550 MB more** than its working figure, which the
  spike measured from a card's allocations on a 2880 × 1920 photo. Not fitted from one machine and
  random weights: the margin covers it, each machine learns its own, and spec 005's local session
  fits the figures.

It does not show the real weights loading, sane depths (CI's `models (cpu)` job, AC2), anything on
a card, or Windows.

## How it ran

- **Machine:** Linux, an Intel Xeon at 2.80 GHz with 4 cores, 16 GB of memory.
- **Runtimes:** `depth_pro` and `moge`, their `cpu` builds (Python 3.14.9, torch 2.14.0+cpu),
  installed by `npm run bench:runtime -- depth_pro` and `-- moge`. GitHub's archive host is out of
  reach here, so each pinned source was put in `<data>/runtimes/<id>/downloads/<sha256>` from a
  clone with `git archive --format=tar --prefix=<repo>-<commit>/ <commit> | gzip -n`; all three
  sha256s matched the pins.
- **Weights:** random, with the real shapes, from the upstream code in each runtime: Depth Pro's
  network built at fp32 and its state saved at fp16, as Apple's file is (1,904,340,610 bytes against
  the pinned 1,904,446,787); MoGe-2 and MoGe-3 built from the spike's `configs/`, saved as
  `{"model_config": ..., "model": state}` (1,323,775,503 and 1,323,776,139 bytes against 1,323,815,904
  and 1,481,333,394; MoGe-3's config keeps its refiner and its state one refiner tensor, which the
  node leaves unread). Copies of the three node folders and `source.image`, each file's row pointing
  at its random file, which the store holds by sha256.
- **The graph:** `source.image` on `engine/tests/models/photo-512.jpg` (512 × 230), wired to the
  three nodes, as the bench graphs of task 7 will be. From the repo's root:

```sh
npm run bench:fit -- --nodes <copies> --graph <graph> depth_pro --set precision=fp32
npm run bench:fit -- --nodes <copies> --graph <graph> moge3 --set resolution_level=0 --set resolution_level=9
npm run bench:fit -- --nodes <copies> --graph <graph> moge2 --set resolution_level=0
npm run bench:fit -- --nodes <copies> --graph <graph> moge2 --set resolution_level=9
```
