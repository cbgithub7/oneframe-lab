The cap, `ctx.fallbacks`, the engine's retry and the holder fit all worked on the card, and the
measured estimates held. One clause is not met by the measure the plan sets: "does not rise".
The evidence below points to the measure, not a spill. Whether to accept that, or to change the
measure and rerun, is the owner's call.

## Finding 4: the shared-growth measure counts the CUDA context

The bench reads growth as the largest sample less the first. Every CUDA process here holds about
64 MiB (67 MB) of shared memory of its own. When the first sample lands before the context has
made that allocation, a run that never spills reads as a rise of up to 64 MiB. Here, the
control's real spill also showed as 64 MiB.

A diagnostic took every sample, using the bench's own functions from a script outside the repo,
not part of the plan:

| Run | Shared usage samples (MB, every 250 ms) | Bench's "growth" |
| --- | --- | --- |
| Inside the cap (defaults, fit on) | 67 flat | 0 |
| Overrun, `ctx.fallbacks` (`step_oom` 1) | 52, then 67 flat | 15 |
| Overrun, engine's retry (`oom` 1) | attempt 1: 65, 67, 65 · attempt 2: 4, then 67 flat | 63 |
| Control spill (`spill_mb` 256) | 65, 65, then **132** to the end | 67 |

No overrun process went above the 65 to 67 MB that a run inside the cap holds. The control went
to 132 MB, so the counter does see a spill. A measure that judges an overrun by whether it rises
above a run inside the cap, sampled in the same step, would tell the two apart. The report could
also keep the samples. That changes how the plan's rule is read, so it is left to the owner.

## What changed since the first run

Commit `4f1bc15`, in `engine/src/oneframe/bench_fit.py`:

1. The bench's scheduler learns nothing between runs. `LearnedStore(None)` learned in memory,
   which let the control's peak correct the overrun's estimate off the card.
2. The holder counts its own CUDA context (step 1's size). It aims at the middle of the window
   between the node's need after its first change and at its defaults, and the budget is read
   while the holder is up.
3. The report says when the holder did not show the change, when an overrun was not exercised,
   and when the control's counter did not rise.

Three tests added in `engine/tests/test_bench_fit.py`, none removed. The learning test fails on
the old bench: the estimate went from 140 to 340 MB after an overshooting run.
